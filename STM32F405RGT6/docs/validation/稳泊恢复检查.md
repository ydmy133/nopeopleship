# 稳泊锚点恢复检查

日期：2026-10-10。针对当前 FreeRTOS 固件的控制业务模块，仅进行源码检查和主机验证，没有修改固件逻辑，没有上板验证。

验证命令：`python tests/control/check_loiter_recovery.py`。直接编译当前 `control_manager`、传感器/命令保护和全部 Boat 算法；各场景独立进程，隔离静态状态。检查真实内部锚点以及对外 `ControlSnapshot`，不以 UI 地图目标变化代替固件状态。

| 场景 | 主机结果 | 原因 |
|---|---|---|
| 有定位时进入稳泊，GNSS NO_FIX 超过 6 秒；稳泊命令持续收到，恢复到另一船位 | 保留原锚点；失效期间零输出且有效模式仍为稳泊 | 传感器保护只覆盖输出；未改变 `s_last_mode`，重复稳泊没有模式边沿。 |
| 已锁原锚点，GNSS 同时失效，命令年龄超过 5200 ms；`dc_prot=0`、默认停桨策略，恢复后收到稳泊命令 | **复现重新锁点：原锚点替换为恢复时船位** | 超时先切有效模式与 `s_last_mode` 到手动，并停止 BoatApp；新稳泊命令被当作重新入模式，重新调用 EnterLoiter。 |
| 首次进入稳泊时 GNSS 无定位、坐标为零；随后收到有效定位，命令模式保持稳泊 | **锁住 (0,0)，恢复不自动修正锚点** | 入稳泊分支未检查 GNSS/航向有效性，先锁点再最终停推；恢复没有新的模式边沿。若无效时缓存旧坐标，锁定的则是旧坐标。 |

主机原始输出见 [loiter_recovery.log](loiter_recovery.log)。这是当前行为检查，脚本包含对已知问题的复现断言；脚本通过不代表这些问题已修复，也不替代串口/DMA或上位机重连的实际验证。

## 源码边界

- `App/Control/control_manager.c`：稳泊仅在 `mode_edge` 时进入；传感器保护保留模式，命令超时的默认停止策略会改为手动。
- `App/Control/Boat/boat_modes.c`：锚点只在 `BoatModes_LoiterEnter` 中写入；GNSS 串口恢复没有直接写入锚点的调用。
- `App/Control/Boat/boat_app.c`：`EnterLoiter` 同时更新算法锚点及目标诊断。
- `App/Config/app_config.h`：当前 `DISCONNECT_ACTION_STOP_MOTOR`。以上断连复现明确使用 `dc_prot=0`；打开 `dc_prot` 会走另一条返航逻辑，不能把此场景直接套用到返航后的恢复。

真正避免自动重锁需明确“暂时失效/通信恢复”和“用户主动重新设锚”两种生命周期。可在应用控制层保留已确认锚点，使 GNSS 或命令恢复不会自动重新设点；首次无有效定位时拒绝锁点或进入等待定位状态。此检查尚未实施该行为变更，后续还需定义手动取消、明确重新设点和返航结束的处理规则。
